> [!IMPORTANT]
> **Notice:** Logic update for number blocking validation on Gateway 1 addresses the recurring Boom 400 error 'Unable to resolve PN JID for LID: xxx@lid' when receiving private messages from WhatsApp accounts utilizing Linked Identity (LID) formats.

---

### 1. What was the Issue?
* Gateway 1 PM2 logs encountered repeated errors: 'Error: Unable to resolve PN JID for LID: 221694031593653@lid' originating from Baileys updateBlockStatus and handler.js.
* Root cause: Config.blocks (virtual number country code blocklist such as 994, 221, and 212) checked m.sender?.startsWith(no) directly without verifying whether the sender was an actual phone number (@s.whatsapp.net) or an opaque privacy identifier (@lid).
* The numbers comprising an LID (e.g. 221694031593653@lid) are random 15-digit identifiers generated by WhatsApp, not the Senegal country calling code (+221).
* As a result, legitimate users whose random LID happened to begin with 221 were falsely flagged as virtual spammers, triggering automatic block attempts.
* WhatsApp block protocol strictly requires a resolved phone number JID (pn_jid). Because no mapping was available for that LID, Baileys rejected the block request with Boom 400.

---

### 2. What was Fixed?
* Introduced the isBlockedNumber helper in handler.js, ensuring country calling code prefix matching is strictly confined to real phone JIDs (@s.whatsapp.net) and never applied to random @lid strings.
* Replaced all direct client.updateBlockStatus calls in handler.js with safeUpdateBlockStatus from lib/system/block-status.js for queued, error-resilient execution.
* Upgraded lib/system/block-status.js to resolve LIDs to phone numbers via database and contact cache. If unresolved, block attempts are safely skipped rather than causing Baileys to throw exceptions.
* Hardened the global exception catch filter in handler.js to prevent unresolvable LID rejections from sending error responses to users or polluting system logs.

---

### 3. How does this Affect Users?
* Legitimate WhatsApp accounts communicating via LID can now interact with the bot normally without being erroneously blocked.
* The bot no longer issues spurious error replies when receiving messages from LID-based senders.
* Gateway stability is preserved, eliminating Boom 400 log floods while retaining accurate blocking for genuine virtual spam numbers.

---

### 4. The Result
The LID resolution error on Gateway 1 has been completely resolved. The fix has also been synchronized across Gateway 2 and Gateway 3 for comprehensive cluster reliability.
